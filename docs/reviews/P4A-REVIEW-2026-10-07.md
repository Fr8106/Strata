## 0. 结论摘要

**一句话**：现有排障做得扎实（排除矩阵是高质量的二分），但"驱动 bug"的结论**还没有被证据支持**；当前的修复方向合理但有一个**被忽略的代价**——它把内存占用回退到了改造之前的水平；而在下一次占用 GPU 的窗口之前，有一批**不需要 GPU 窗口**的检查可以先做，能显著提高那次窗口的信息量。

四个要点：

1. **证据链有三处需要订正**（§2）：
   - `cudaHostUnregister` 对 4 MiB 子窗口报 invalid argument，这是 API 的**正常行为**，不能作为"驱动记录损坏"的证据。
   - 失败的 pair 0 按排名映射应属于**固定区（未注册区）**，与"已注册 run 内的 src 才挂"的叙述不一致，需要先弄清 src 到底在哪。
   - "段数上限≈5300"与"t9 通过 8192 段"相互矛盾，说明上限不是单纯的段数。
2. **修复本身的代价**（§3）：48 层整层 Mapped 注册 ⇒ 46.8 GiB 全程 pinned，`MemAvailable` 预计 4–6 GiB。这恰好回到了本项目要解决的起点（§1 目标是"让专家页变为可回收"）。这是一次**目标层面的取舍**，应当让用户明确知情后裁定，而不是作为"段数上限的代价"一笔带过。
3. **有更干净的结构方案**（§4）：按 tier 排布 arena，让固定区在地址上**连续**，只注册非固定区的 1–几个大段。这样既绕开"数千小段"，又能真正归还 ~11 GiB。另有"pinned 小环形缓冲 + 多线程拷贝"等不依赖注册的备选。
4. **失败要降级而不是宕机**（§3.3、§6）：加启动自检（canary）与回退梯子；窗口操作加 dead-man 定时器和 VRAM 预检；server 对引擎提前退出要立即感知，而不是轮询到 255 s。

建议的行动顺序见 §9。

## 2. 根因分析的审查

### 2.1 对排除矩阵的评价

矩阵本身可信，建议保留。但它的**逻辑方向是"从干净程序往上堆"**（t7→t15），目前堆到 t15 的 m1 / m48 / p1 都通过，而真正失败的形态（4628 段）**没有在 t15 上下文里复现过**。因此"干净上下文通过、引擎上下文失败"只能说明"差异在引擎里"，不能说明"差异在驱动里"。引擎里除驱动外还有大量自己的内存操作（见 §2.3）。

### 2.2 三处证据需要订正

**(1) `cudaHostUnregister` 4 MiB 窗口报 invalid argument、再注册报 already mapped——这是预期行为，不是损坏证据。**
`cudaHostUnregister` 要求传入当初注册时的**基地址**；对已注册区间内部的子窗口调用会失败，对子窗口再注册会因范围已被注册而报 already registered。这两个结果恰好是"一切正常"时也会出现的现象。该探针只有在**窗口 = 某个已注册 run 的精确 [base, size]** 时才有判别力。建议：重做该探针，或把它从"驱动记录损坏"的证据中删除。

**(2) pair 0 的 src 究竟在已注册区还是未注册区？**
文档说"fill 失败在 pair 0"，同时 §3.1 的日志写明"固定区的 6320 个专家保持未注册"。按计划里的"排名 i → 槽 i"，**pair 0 是排名最高的专家，应当属于固定区（未注册）**。而 §3.3 的结论是"从已注册 run 内的 src 做 HtoD 任何大小都失败"。两者需要对上：

- 若 pair 0 的 src 在**未注册的 pageable 匿名内存**里也失败，那么"数千小段注册损坏"就不是充分解释，问题可能出在**整块 arena 的某种属性**或上下文级状态；
- 若 pair 0 的 src 实际在已注册区，需要说明为什么（排名与固定区的映射关系是否与我的理解不同）。

建议做一个 **3 路对照**：同一次启动里，分别从 ① 已注册 run 中部、② 未注册的固定区 blob、③ 全新的 pageable 缓冲区，各做一次小 HtoD，记录 rc。三者的组合会直接给出"问题与注册有关/与 arena 有关/与上下文有关"。

**(3) "段数上限≈5300"与"t9 通过 8192 段"矛盾。**
文档同时给出：t9 干净上下文 8192 段 × 3.3 MiB 通过；引擎里 4628 段通过、9256 段被拒（约在 3900 处）。三个"上限"：3900 / 4628 / 8192 / "≈5300"，说明它不是单纯的段数上限，更可能是**与上下文状态或总映射量共享的预算**。在得到"变量 vs 阈值"的清晰关系之前，不应把 5300 当作约束写入设计（它已经被用来决定 48 层方案并带来 ~11 GiB 的代价）。建议用 §2.4 的"引擎内阶梯"实验把它拆成：段数、单段大小、总字节、上下文状态四个因素，每次只变一个。

### 2.3 数字上还有一处缺口

- 全量专家 arena = 46.84 GiB；固定区 ≈ 11.2 GiB（6320 个）；注册总量 34.87 GiB。
- 46.84 − 11.2 = 35.64 GiB，而实际注册 34.87 GiB，**有约 0.77 GiB（平均每个 run ≈ 170 KiB）没有被注册，也不属于固定区**。文档在 §3.5 也写了"原设计 35.6 GiB"。

这 0.77 GiB 可能来自 run 边缘按页/按某个对齐做的向内取整，或被跳过的短 run。这点重要，因为**blob 起止不按页对齐**（2176000 B = 531.25 页）：如果 run 向内取整，处于 run 边缘的 blob 会**跨越"已注册/未注册"边界**，一次 `cudaMemcpy` 的源区间一部分在注册范围内、一部分不在。这正是一种能让驱动返回 InvalidValue 的形态。即使它不是当前失败的原因，也应该排除，因为 48 层方案里同样存在"层与层之间的边界"（不过整层注册时相邻层若连续排布则边界不会出现在同一 blob 中）。

### 2.5 不需要 GPU 窗口、现在就能做的事

1. 查看之前失败运行的内核日志：`sudo dmesg -T | grep -iE 'nvrm|nvidia|uvm|xid'`，或 `journalctl -k -b`。驱动层若有告警（页锁定失败、UVM 错误），这里会有。
2. `nvidia-smi -q | grep -iE 'addressing|link|gen|width'`：看 Addressing Mode（HMM/ATS/None）与 PCIe 实际链路（见 §5.2，同时验证 PCIe 是否降速）。
3. 静态审代码：`register_pcie_alias` 的取整方向、`release`/`release_fixed_tier` 的取整方向、fill 之前是否有任何触及 arena 地址的 madvise/mremap；整个引擎里是否有 `fork`/`popen`/`system`。
4. **立刻把 `/tmp/mmtest/` 复制到持久位置**（见 §8）。
5. 小显存的复现程序（t15 形态，设备侧仅需几百 MiB）在**不停 LLM** 的情况下运行是否可行：swift15 占 30.7 GiB / 31.39 GiB，剩余约 0.7 GiB。如果 record-replay 程序的设备占用控制在 ~300 MiB 以内，可以并行运行；但主机侧要先检查 `MemAvailable`，防止 pin 大量内存把 LLM 服务挤出去。**这一点需要先评估风险再做**。
6. 若环境允许，尝试 `CUDA_LOG_FILE=stderr`（CUDA 12.9 起提供的驱动错误日志环境变量，13.0 应当支持，待核实）。它常常能给出 InvalidValue 的**具体原因**，价值远高于盲猜。该变量加到下一次窗口的引擎环境里即可。

## 3. 当前修复方案的评审（48 层整层 Mapped 注册）

### 3.1 优点

- 段数从 4628 降到 48，t15 里 m48 通过，规避了"数千段"的形态；
- Mapped 的需求理由陈述清楚；
- `release()`/遥测语义诚实；
- 提交粒度清晰，二进制与源码的不一致也被明确指出（"部署的 engine/strata 还是旧版本"）。

### 3.2 需要明确的风险

**(1) 内存目标回退。** 本项目 §1 的目标是"pinned/unevictable 显著下降，专家页变为可回收"。48 层整层注册后：

- 46.8 GiB 专家 arena **全程 pinned**，等同于改造之前的 P0 基线；
- 交接文档预计 `MemAvailable` 4–6 GiB（并建议必要时把对话缓存从 6144 降到 2048 MiB 换 4 GiB）；
- 机器同时有 PLE 26.8 GiB 的文件映射（page cache 竞争者）、对话缓存、KV 主机侧部分；swap 只有 8 GiB，而 pinned 页不可换出。

这意味着 P4-A 实质上是"**用 ~11 GiB 的内存余量换 prefill 约 2×**"，并且把系统带回到最初出现内存紧张的状态。这未必是错误选择，但应该：① 写进交接文档的"取舍"一节；② 让用户在知情前提下裁定；③ 给出内存安全的验收线（见 §7）。

**(2) zero-copy 的收益是假设，未测。** 文档承认"GPU kernel 直接解引用 Mapped host 指针与 cudaMemcpy 路径的性能差未测"，且 t15 的"通过"只证明了注册和拷贝不报错，**没有任何 kernel 实际通过映射指针读取并计时**。建议在引擎窗口之前，用一个小程序测：对 ~1 GiB 的 Mapped 区域，kernel 读取吞吐 GB/s、与 `cudaMemcpyAsync` 的对比、以及 `nvidia-smi` 报告的 PCIe 链路代数/宽度。

**(3) 屋顶线（roofline）核算缺失。** 本机 5900X 平台的 PCIe 为 4.0 x16（约 25 GB/s 量级）。若 prefill 的一个 chunk 需要读遍非驻留专家（约 24 GiB 量级），单次 chunk 的 PCIe 时间下限约 1 s；因此"5.5–6k tok/s"的上限取决于 chunk 里 token 数。请把"目标 5.5–6k tok/s"与"chunk 大小、非驻留字节、PCIe 实测带宽"算一遍，确认目标没有超过物理上限（P0 基线 5.5–6k 是实测的话则无此担忧，但应在文档里写明数字来源）。

**(4) 修复没有在引擎里验证过。** 目前证据只有 t15 的 m48。引擎里"重上下文"这一变量正是之前挂掉的原因，所以 m48 在引擎里是否真的过，仍是未知数。

### 3.3 建议：加上"注册自检 + 回退梯子"

把"驱动状态相关的故障"从**宕机**降为**降级运行**：

```
注册完成后，立即做 canary 自检：
  对 每层 的若干采样点（run 中部、近边缘、跨相邻 blob）各做一次小的 HtoD（几 KiB~2 MiB），检查 rc 并校验内容
全部通过 → 继续
任一失败 → 记录详情（ptr/size/flags/rc/CUDA_LOG），按梯子回退：
  L1：每层 Portable（不带 Mapped）
  L2：不注册，走 pageable（等同 P1 的行为）
  并打印明确的降级警告；服务继续起来，并在 /health 或日志里标出"降级模式"
```

好处：

1. 驱动/内核更新后即使复发，服务也不会宕机；
2. 梯子每一级的结果本身就是**诊断数据**（Portable 过而 Mapped 不过 ⇒ 指向 Mapped 映射；两者都不过而 pageable 过 ⇒ 指向注册本身）；
3. 与 §6 的"server 在 255 s 后才发现失败"问题互补。

同时建议加一个**总开关**（如 `STRATA_PCIE_ALIAS=0`）：与 P1/P2/P3 的三开关风格一致，出问题时无需重编译即可关闭 P4-A。

## 4. 方向性建议：更干净的备选方案

当前方案要解决的是"**固定区页被整层 pin 住，无法归还**"。根源在于固定区的专家在 arena 里与非固定区**交错排布**（按层、按专家 id 排序），所以只能按整层注册。下面是几个备选：

| 方案 | 思路 | 优点 | 缺点/风险 | 估计工作量 |
|---|---|---|---|---|
| **A 现状** | 48 层整层 Mapped 注册 | 已实现，t15 通过 | 46.8 GiB 全程 pinned；引擎内未验证 | 0（只需验证） |
| **B tier 有序 arena** | 加载 arena 时按 profile 排名把**固定区专家放进一块连续区域**，其余专家放另一块连续区域（需要每个专家的 offset 表，变长 blob 本来就有）。只对"非固定区"这块注册，1 段或按 ~2–4 GiB 切成几十段；固定区这块保持普通匿名页，预填后整块 `madvise(DONTNEED)` / `munmap` | 段数极少（规避驱动问题）；**真正归还 ~11 GiB**；与本项目"可回收"的目标一致；profile 每次启动才读，tier 变更只发生在重启，天然契合 | 要改 loader 的布局与 offset 表；adapt 换入仍通过 offset 查找，需要确认没有"按 id 线性寻址"的假设；每次重启要先读 profile 再装载 | 中（~1–2 天，视 loader 结构而定） |
| **C pinned 小环形缓冲** | 不注册 arena。预留 2–4 个 128–256 MiB 的 pinned 暂存块，CPU 多线程 memcpy 从 mmap/匿名页 → 暂存块，异步 H2D 并流水线化 | 仅 pin 数百 MiB；完全不依赖注册大量内存；P1 mmap 的内存收益保留 | 占用 DDR4 带宽（拷贝读写 2×）；峰值取决于 CPU 线程数；prefill 速度介于 3.1k 与 5.5k 之间，需实测 | 中 |
| **D HMM 直读** | 若 `PageableMemoryAccess` 可用，让 GPU 直接访问普通 mmap/匿名内存（可配合 `cudaMemAdvise` 设置 preferred location = CPU、accessed-by = GPU，避免迁移） | 代码最少，完全不注册 | 行为依赖驱动/内核；缺页迁移策略会影响带宽；需要实验 | 先 1–2 小时做可行性试验 |
| **E 回到 P1** | 接受 prefill ~3.1k tok/s，保持可回收 | 零风险，内存最好 | 长 prompt 慢约一倍 | 0 |

**推荐顺序**：

1. 先用现有二进制在**一个设计良好的窗口**里验证 A（§6、§9），因为它已经造好；
2. 无论 A 是否通过，都先评估 **E 的实际代价**：用户的典型 prompt 长度分布是什么？prefill 从 3.1k 提升到 5.5–6k 对日常体验的实际收益是多少（例如 32K 的 prompt：约 10 s → 约 5.5 s）？如果日常 prompt 多在几 K 以内，收益很小；
3. 若要保留可回收目标，**B 是最值得投入的结构方案**；C 和 D 作为"不依赖大规模注册"的低风险探索，在 B 之前或并行用小实验验证。

## 5. 附加技术点

### 5.1 固定区的 RAM 归还

即便在 B 方案里，固定区若用**匿名页**，`madvise(MADV_DONTNEED)` 会**丢弃内容**（与文件映射不同）。这是正确的前提是：预填、`verify_slot` 全部完成，且之后没有任何路径需要再从固定区读取（例如 GPU 内核异常后的回退、`--vram-elastic`——已互斥）。建议在 release 前加一个断言/计数器（"固定区 blob 被读取"），并在 release 后遇到读取时**报错而不是静默读到零**。

### 5.2 PCIe 链路状态

请在 P0 基线和每次窗口里记录 `nvidia-smi -q` 的 PCIe 当前/最大代数与宽度。显卡空闲时 PCIe 常会降速（节能），在 Mapped 零拷贝下链路降速会直接放大 prefill 的时间；基线与对比应在同一链路状态下测。

### 5.3 注册总字节与 RAM

请核实：除 arena 外，PLE 的 26.8 GiB 映射、vision、MTP 等是否也被 `cudaHostRegister`？所有注册字节加起来相对 `MemTotal`（约 62 GiB）是多少？若总量逼近物理内存，驱动在 pin 时可能出现部分失败或触发 OOM。这是"4628 段全过但换形态失败"的另一个可能线索，也与 §2.2(3) 的预算问题相关。

### 5.4 fork 与 pinned 页

若引擎或 server 在注册之后创建子进程（`popen`、`system`、`subprocess` 等），内核对 pinned 页会做 COW 处理，可能使父进程的 pin 与页表脱节。该点可用 `strace -f -e trace=process` 一次性排除。

## 6. GPU 窗口与运维规则审查

交接文档的规则（停与拉必须在同一脚本内闭环、`trap` 兜底、停之前征得同意）是对的，但有几处薄弱：

1. **`trap` 无法覆盖所有终止方式**：脚本被 `SIGKILL`、SSH 断开、父会话退出时，`trap` 不会执行。建议在**停 LLM 之前**先注册一个 **dead-man 定时器**：

   ```
   systemd-run --on-active=25m --unit=llm-deadman \
       docker start NInfer-kaushikvira-swift15
   # 实验正常结束后：
   systemctl stop llm-deadman.timer llm-deadman.service
   ```

   这样即使脚本和会话都死了，服务也会在预定时间被拉回。定时时间应略大于实验最长时间。
2. **启动前预检 VRAM**：上一次窗口里"引擎 weight arena 直接 OOM"，说明 `docker stop` 之后显存没有及时释放（或根本没停到位）。脚本里应循环等待 `nvidia-smi --query-gpu=memory.used --format=csv,noheader,nounits` 小于某个阈值（例如 1 GiB），超时则**中止实验并恢复 LLM**，而不是继续启动引擎。
3. **server 对引擎提前退出要立即感知**：现在引擎 exit 1 后 server 仍轮询到约 255 s。一次窗口里这白白浪费 4 分多钟，且服务状态模糊。让 server 对子进程 `poll()`，退出即快速失败。
4. **systemd 重启策略**：`strata.service` 的 `Restart` 会"自动拉起，kill 无效"。对**确定性失败**应配置 `StartLimitIntervalSec`/`StartLimitBurst`，避免失败后无限循环占用 GPU 与 8088。
5. **窗口前预置全部观测**：一次窗口的成本很高，应一次带齐：`CUDA_LOG_FILE`、注册序列导出、`strace` 的 mm/process 子集、3 路对照拷贝、canary 自检、`/proc/<pid>/status`（`VmPin`/`VmLck`/`VmRSS`）、`/proc/meminfo`、PSI、`nvidia-smi -q` 的 PCIe 链路快照。
6. **同一脚本里完成"实验→恢复→校验"**：恢复后检查 8088 健康（`/health` 或一次短请求），不通过则报警。

## 7. 验收与指标

交接文档的验收线是"prefill ~5.5–6k tok/s、fixed evict attempts 恒 0、RSS ≈ 46.8 + 开销、MemAvailable ≈ 4–6 GiB 时酌情调参"。建议补充：

| 类别 | 指标 | 说明 |
|---|---|---|
| 性能 | prefill tok/s（按 1K/8K/32K 三档）、decode tok/s 中位数与 p95、首 token 延迟 | 不能只看 prefill 一个数；decode 可能被 pinned/占用带宽影响 |
| 内存 | `VmPin`/`VmLck`、`RssAnon`/`RssFile`、`MemAvailable`、`Unevictable`、swap 使用量与换入速率 | 同时记录空载与 262K 上下文填满后的值 |
| 压力 | `/proc/pressure/memory` 的 some/full avg10、`workingset_refault_file`、`pgmajfault` | `MemAvailable` 单项会误导，因为 page cache 计入 |
| 稳定性 | 连续 N 次启动/停止循环（含 profile 换血）、`dmesg` 无 NVRM 报错 | 确定性问题往往只在特定顺序下出现 |
| 降级 | canary 自检结果、降级级别（L0/L1/L2） | 若上线后经常降级，说明该方案不稳 |

**建议的内存安全线**（需用户确认后定稿）：满载上下文下 `MemAvailable` ≥ 8 GiB；swap 换入速率为 0；PSI memory `full` avg10 < 1%。若达不到，优先降低对话缓存或回退到方案 B/E。

另一点：交接说"P4 四臂对比（用户搁置，改用实际使用测试模式）"。尊重用户的取舍；但**实际使用测试**也需要最少量的客观数据（至少 prefill/decode 的前后对比和内存曲线），否则 P4-A 是否"值得"就只能凭印象。建议在使用期间让服务端落盘一份简要的请求级日志（prompt token 数、prefill 时间、decode 速率、内存快照）。
