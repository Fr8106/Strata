- 被评估文件：[OPTIMIZATION-SUGGESTIONS-2026-10-07.md](OPTIMIZATION-SUGGESTIONS-2026-10-07.md)（专家原文存档；作者自述只看文档、未看代码和剖析）
- 与上一份《P4-A 交接文档审核》（[P4A-REVIEW-2026-10-07.md](P4A-REVIEW-2026-10-07.md)）的关系：那份管**排障正确性**，这份管**优化方向与优先级**，两者不冲突。
- 总评：**合理，且"先测再定"的立场正确**。最大的价值是把优化重心从 P4-A 注册线移到"prefill 流水线 + 前缀缓存"——我同意这个转移（P4-A 的 3.1k→6k 是真实但有限的收益，前缀命中可以直接跳过 prefill）。两处 roofline/预取框架需要修正，见 §2。

## 1. 当场核实的机器事实

| 专家陈述 | 核实结果 |
|---|---|
| 方向四"12 个物理核 vs 24 线程" | **正确**：`lscpu` 实测 12 核 / 24 线程（CPU 字符串 "5900X 12-Core"，L3 64 MiB = 2 CCD × 32 MiB，双 CCD 绑定建议成立） |
| "本机 PCIe 4.0 x16 约 25 GB/s" | 与探针实测 ~28.4 GB/s 一致（量级对） |
| Nsight Systems 抓时间线 | **工具已就绪**：`/usr/local/bin/nsys` + `/opt/nvidia/nsight-compute`，无需安装；抓 prefill/decode 时间线需要 GPU 窗口（引擎占整卡） |
| 对话缓存 6 GiB | 对：`--conversation-cache-mib 6144` |

## 2. 需要修正的两处框架

1. **"一个 chunk 读遍 24 GiB 非驻留专家 ⇒ ~1 s ⇒ 吞吐 ≈ chunk/1 s" 过于悲观**，不作为排序依据：
   - 5.5–6k tok/s 是 **P0 在本机实测**（pinned arena、同卡同 PCIe），是 ground truth，roofline 推算与实测冲突时以实测为准；
   - 路由质量高度偏斜：固定 tier（top-6320，25.7%）捕获绝大多数命中（自适应层 hit 96% 实测），**每 chunk 实际读的非驻留字节远小于 24 GiB**——24 GiB 是"最坏全覆盖"上限，不是典型值；
   - profile 预填（12641 slots）是启动时一次性行为，非每 chunk 重复。
   - 结论：该 roofline 保留为**核对工具**（窗口里顺手记 PCIe 链路状态），不否定 5.5–6k 目标。
2. **"l+1 层专家集合几乎可预知，整层预取"** 表述过强：层 l+1 的路由结果只在算完层 l 后才知道，"整层非驻留集"（≈0.73 GiB/层）是安全上界但浪费；实用做法是用**前一 chunk 的路由分布预测下一层热集**，只预取热集。预取落地形式 = 方案 C 的 pinned 环形缓冲，两者应合并设计。

## 3. 逐方向采纳决定

| 方向 | 评估 | 决定 |
|---|---|---|
| 一 chunk 调优 | 配置级 A/B，窗口内顺手测 | **采纳**（并入窗口测量批次） |
| 一 双缓冲层预取 | 合理，但预取缓冲即方案 C 的 pinned 环形缓冲；"拿到 P4-A 大部分收益"的前提是 DDR 2× 拷贝带宽不反噬，需实测 | **排队**，与方案 B/C 决策合并（不单独立项） |
| 二 请求级日志（prompt 长度/prefill 时间/前缀命中率/内存快照） | 三项优化方向的共同数据入口，serve 侧代码，**不需窗口** | **立即采纳** |
| 二 扩缓存 / NVMe KV 持久前缀 / 前缀匹配策略 | 命中率未知前是纯推测 | **缓**，等日志数据 |
| 三 usage 播种（profile → usage 初值） | 消灭"重启后 usage 从 0、早期 victim 近任意"，P3 的自然延伸，小改动 | **立即采纳** |
| 三 TinyLFU/ARC 大小感知 | MoE 路由偏斜，理论有空间；现策略 hit 96%（自适应层），收益上限有限 | **排队**，先看现策略命中率数据 |
| 三 spec 深度联动 / 逐层配额 | 合理，中等复杂度 | **排队** |
| 四 线程 12v24 / CCD 绑定 / 大页 / AVX2 点积 / FCLK 1:1 | 五条都合理且便宜；FCLK 要动 BIOS，其余配置级 | **采纳为 sweep**，先取 decode 基线（nsys + decode tok/s p95）再逐项测 |
| 五 热度分级量化 | 方向真实（Fiddler / MoE-Infinity / HOBBIT / Pre-gated MoE 都是真研究），但要 perplexity/任务集质量评估 + pack 重做 + 内核混合位宽支持，成本最高 | **不启动**，留作研究跟踪 |
| 六 AM5/PCIe5/DDR5 升级 | 事实正确（Zen4 = PCIe5 + DDR5 + AVX-512）；但 **P0 在 Gen4 上实测已达 5.5–6k**，"PCIe 是瓶颈"的前提不成立，收益未证实 | **列为用户决策的付费选项**，不预设收益 |
| 七 基准套件 / metrics / canary+梯子 / 解耦开发环境 | 前两项便宜且与上一份审核 §7/§8 一致；canary+梯子已在 P4A 审核采纳；**"助手 LLM 与被测引擎抢 GPU，窗口是最大流程成本"观察正确** | 基准套件（轻量版）+ metrics **立即采纳**；解耦方案（助手 LLM 移机/云、加便宜小卡、维持现状零成本）**列为用户决策** |

## 4. 优先级核对

专家排序（1 时间线+日志 → 2 预取+chunk → 3 前缀缓存 → 4 策略 → 5 CPU 调优 → 6 量化/硬件）总体成立。一处细化：**前缀命中率测量（#1 的一部分）比双缓冲预取实现（#2）更便宜，且若命中率高，#3 的收益超过 #2**——执行上"日志先落、预取缓做"，与专家"先测再定"自洽。

## 5. 立即执行清单（不需 GPU 窗口）

1. serve 侧请求级日志：prompt token 数、prefill 耗时、decode 速率、前缀命中率、内存快照（落盘 JSONL）。
2. usage 播种：profile 排名 → usage 初值。
3. 轻量基准脚本：固定 workload + 固定种子 + 噪声记录（并入 §10 的 24 h 压测项）。
4. metrics 补齐：hit rate、swap 字节、major fault、spec 接受率（tier 份额 / fixed_evict_attempts 已有）。
5. 待窗口：nsys 抓 prefill/decode 时间线（工具已装）+ decode 基线 + PCIe 链路快照。

用户决策项（与上一份审核的三裁定合并）：① 前缀缓存投入（等命中率数据）；② 解耦开发环境的成本方案；③ AM5 升级是否值得（当前证据不支持"PCIe 瓶颈"前提）。
